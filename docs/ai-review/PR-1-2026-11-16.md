## ✅ 优点

- **触发条件设计合理**：`pull_request` 使用 `opened, synchronize`，覆盖了 PR 创建和后续推送两种场景。
- **防死循环机制**：通过 `[skip review]` 提交信息配合 `if` 条件跳过自身提交，思路正确。
- **diff 缓冲区保护**：`maxBuffer: 10 * 1024 * 1024` 防止大 diff 撑爆缓冲区，考虑周到。
- **API 错误处理**：对 `res.ok` 做了判断并输出状态码与响应体，便于排查。
- **报告落盘 + 阻塞合并**：将审查结果写入独立文档，并通过 `exit 1` 配合 branch protection 阻止合并，闭环完整。
- **注释清晰**：关键步骤都有中文注释说明意图，可读性好。

## ❌ 问题

### 1. 严重程度：高 — `git push` 在 PR 分支上可能失败或产生竞态
- **位置**：`scripts/ai-review.mjs` 第 6 步 `execSync('git push')`
- **原因**：
  - `actions/checkout` 默认使用 `GITHUB_TOKEN` 检出，但 `permissions.contents: write` 虽已声明，**fork PR 场景下 `GITHUB_TOKEN` 是只读的**，push 会直接失败。
  - 即使同仓库 PR，若在审查期间 PR 分支有新提交，`git push` 会因非 fast-forward 被拒绝，导致整个 job 失败（即使审查本身通过）。
- **修改建议**：
  - 明确限制该 workflow 仅对同仓库 PR 生效：在 job 的 `if` 中增加 `github.event.pull_request.head.repo.full_name == github.repository`。
  - push 前先 `git pull --rebase origin ${{ github.event.pull_request.head.ref }}`，或使用 `git push --force-with-lease` 并处理失败情况（失败时不应让整个审查 job 挂掉，可 `try/catch` 后仅告警）。

### 2. 严重程度：高 — 审查报告提交会污染 PR 分支并触发新的 CI
- **位置**：`scripts/ai-review.mjs` 第 6 步
- **原因**：把报告 commit 到 PR 分支本身，会让 PR 的 diff 里混入 `docs/ai-review/*.md`，且每次推送都会产生新 commit。虽然用 `[skip review]` 跳过了本 workflow，但**其他 CI（测试、lint 等）仍会被触发**，造成资源浪费和噪音。
- **修改建议**：改用 PR 评论（`gh pr comment` 或 GitHub API）发布报告，或提交到独立分支/使用 artifact 上传，避免污染 PR 分支。

### 3. 严重程度：中 — `head_commit` 在 `pull_request` 事件中可能为 null
- **位置**：`.github/workflows/ai-review.yml` 的 `if: ${{ !contains(github.event.head_commit.message, '[skip review]') }}`
- **原因**：`pull_request` 事件的 payload 中**没有 `head_commit` 字段**（那是 `push` 事件才有的），该表达式会求值为 `contains(null, ...)`，行为不可靠，防死循环的 `if` 实际可能不生效。
- **修改建议**：改用 `github.event.pull_request.head.commit.message`，或直接依赖脚本内的判断逻辑（例如检查最新 commit message）。

### 4. 严重程度：中 — `data.choices[0].message.content` 未做防御
- **位置**：`scripts/ai-review.mjs` 第 3 步之后
- **原因**：若 API 返回结构异常（如 `choices` 为空、被内容过滤），会抛 `TypeError`，错误信息不友好。
- **修改建议**：增加可选链与兜底：`const review = data?.choices?.[0]?.message?.content; if (!review) { console.error('❌ 审查结果为空', JSON.stringify(data)); process.exit(1) }`。

### 5. 严重程度：低 — 缺少 `timeout` 与重试
- **位置**：`scripts/ai-review.mjs` 的 `fetch` 调用
- **原因**：DeepSeek API 偶发慢响应时，job 可能长时间挂起直至 GitHub 默认超时（6 小时）。
- **修改建议**：给 `fetch` 加 `signal: AbortSignal.timeout(60_000)`，并对 5xx/429 做简单重试。

### 6. 严重程度：低 — 文件末尾缺少换行
- **位置**：`.github/workflows/ai-review.yml` 与 `scripts/ai-review.mjs` 末尾
- **原因**：diff 显示 `\ No newline at end of file`，不符合多数项目的 lint 规范。
- **修改建议**：补上末尾换行。
